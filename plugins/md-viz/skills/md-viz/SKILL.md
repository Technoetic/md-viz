# 마크다운 시각화

호출 뒤에 적힌 파일 경로 또는 제공된 본문을 대상으로 한다. 게시 위치나 원하는 도구를 지정하면 따른다. 대상이 생략됐으면 현재 대화에서 명확하게 가리키는 문서를 사용하고, 후보가 여럿이면 어느 파일인지 한 번만 묻는다.

## 문서를 꾸미는 방식

1. **기본 호출은 시각화 도구 25종과 Markdown 표현 6종을 함께 검토한다.** 아래 표에서 도구와 표현을 하나씩 원문의 질문·자료에 대응시킨다. 본문에서 참조하는 표·코드·그림·소리에도 단서가 있다. 같은 데이터라도 구성 비율, 시간에 따른 변화, 계산 규칙처럼 독자에게 주는 답이 다르면 여러 도구로 풀어낸다.
2. 대응시킨 도구마다 실제 출력을 만들고 원고에 넣는다. 25종 모두 쓰임이 있으면 기본 호출에서도 25종을 사용한다. 빠진 후보는 필요한 입력이 있는지, 같은 그림으로 이미 설명됐는지, 게시 환경에 맞게 정적으로 내보낼 수 있는지 한 번 더 살핀다. 결과가 많으면 핵심은 본문에 두고 나머지는 주제별 접이식 도감이나 같은 문서에서 연결한 갤러리에 모은다.
3. 원문의 값·단위·날짜·관계·출처를 그대로 사용한다. 선의 방향과 의미를 원문과 대조한다. 값이 없는 비교는 정성적으로 표현하고, 계획·예상은 실측과 구별한다. 그림 바로 아래에는 핵심을 짚는 짧은 설명을, 이미지에는 내용이 드러나는 대체 텍스트를 붙인다.
4. 해당 꼭지에서 그림이 답하는 문장 가까이에 실제 도식 또는 이미지 참조를 삽입한다. 기존 원고, 링크, 코드 예제와 작성자가 넣은 그림을 보존한다. 생성 파일에는 절·주제가 드러나는 안정적인 이름을 써서 재실행 시 같은 그림을 갱신한다. 문서 안에 같은 삽입물이 쌓이지 않게 한다.

**호출 범위.** ‘그림 한 장만’, ‘코드만’, ‘Mermaid만’처럼 지정하면 그 범위가 우선한다. ‘21종 전체 시연’은 도식·차트 21종, ‘25종 전체 시연’은 구문 강조·수식까지 포함한 도구 25종을 다룬다. ‘Markdown 표현 6종 시연’은 아래 여섯 표현을, ‘전부 시연’은 도구와 표현 모두를 다룬다. 각 시연에서는 해당 항목의 결과물이나 미사용 사유를 보여 준다. 비교용 입력을 지어낼 때는 각 결과에 ‘시연용 예시’라고 밝힌다.

## Markdown 표현 6종

기본 호출에서 다음 단서를 찾으면 독자가 해당 정보를 쓰는 자리에 표현을 직접 넣는다. GitHub 문법과 대체 표현을 작성할 때는 [문서에 붙여 넣는 예시](references/markdown-patterns.md)를 참고한다.

| 원문에서 찾을 단서 | 적용할 표현과 확인할 점 |
|---|---|
| 지점·경계·경로의 **실제 위치** | **지리 지도**. GitHub에서는 `geojson` 또는 `topojson` 코드 블록을 쓴다. 좌표 순서(경도, 위도)와 지명을 원자료와 대조한다. 지도를 표시할 수 없는 곳에는 지명·좌표 목록 또는 지명이 적힌 정적 지도를 제공한다. |
| 버전·라이선스·빌드 상태를 확인할 근거 | **배지**. 값이 보이는 이미지에 같은 뜻의 대체 텍스트를 붙이고 릴리스·라이선스·해당 워크플로로 연결한다. 오프라인에서는 로컬 배지나 텍스트 링크를 쓴다. |
| 목록에서 구별해야 하는 상태나 항목 | **이모지**. 같은 뜻에는 같은 기호를 쓰고 `✅ 완료`처럼 텍스트를 곁들인다. GitHub 단축 코드가 풀리지 않는 환경에는 유니코드 또는 글자 레이블을 쓴다. |
| 조작 전후·시간에 따른 화면 변화 | **애니메이션 GIF**. 변화가 보이는 짧은 구간을 해당 절에 삽입하고, 정지 이미지나 짧은 단계 설명도 같은 곳에서 읽을 수 있게 한다. |
| 독자가 찾아갈 파일과 상위 폴더 | **디렉터리 트리**. 대상 경로를 확인하고 필요한 가지를 `text` 코드 블록에 들여쓴다. 이름·대소문자·부모 경로를 실제 구조와 대조한다. |
| 작업에 앞서 알아야 할 사항·결과 | **GitHub 알림**. 참고는 `NOTE`, 요령은 `TIP`, 필수 정보는 `IMPORTANT`, 문제를 피하려는 사전 경고는 `WARNING`, 손실처럼 부정적 결과에 주의를 줄 때는 `CAUTION`을 쓴다. 일반 Markdown에서는 뜻이 드러나는 굵은 레이블과 인용문으로 옮긴다. |

## 코드 구문 강조·수식 표시

코드의 들여쓰기·문자열과 수식의 기호·첨자를 보존한다. 한 블록에는 렌더러 하나를 적용한다. 서로 다른 코드 예제나 수식에 별도의 설명 목적이 있으면 네 엔진을 나누어 쓸 수 있다. 예를 들어 정적 Python 예제는 Shiki, 화면에서 바뀌는 JavaScript 예제는 highlight.js로 보여 준다.

| 도구 | 쓸 때 |
|---|---|
| **Shiki** | 정적 문서 사이트를 빌드할 때, 언어가 지정된 코드 블록을 미리 강조한 HTML로 만든다. |
| **highlight.js** | 브라우저에서 새로 표시하는 코드 블록에 구문 강조를 적용할 때 쓴다. 언어를 알면 명시하고 테마 CSS를 함께 적용한다. |
| **MathJax** | TeX 수식에 필요한 확장을 지원하거나 수식을 SVG로 내보낼 때 쓴다. |
| **KaTeX** | 지원하는 TeX 수식을 빌드 단계에서 HTML과 MathML로 출력할 때 쓴다. HTML과 함께 CSS·글꼴도 제공한다. |

GitHub README와 Obsidian에서는 코드 블록의 여는 줄에 `js`처럼 언어 이름을 붙이고, 본문 수식은 `$…$`, 독립된 줄의 수식은 `$$…$$`로 감싼다. 금액과 코드 안의 달러 기호는 그대로 둔다. 네이버 복사용 원고는 코드를 복사 가능한 텍스트로 유지하고, 수식 서식이 유지되지 않는 곳에서는 수식 PNG와 읽을 수 있는 식 설명을 함께 제공한다.

강조 결과에서 복사한 코드와 원문을 대조한다. 수식은 분자·분모나 첨자가 의도한 위치에 표시되는지와 지원하지 않는 명령이 있는지 확인한다.

## 어떤 도구를 쓸까?

| 문서가 담고 있는 것 | 어울리는 도구와 판단 기준 |
|---|---|
| 처리 단계와 분기, 일정 | **Mermaid**로 흐름·분기·간트 차트를 그린다. |
| 메시지를 주고받는 순서 | **PlantUML**로 참여자별 요청과 응답을 나란히 놓는다. |
| 연결 구조와 설계 | **Graphviz**는 의존 관계의 자동 배치, **D2**는 구성요소를 그룹으로 묶은 구조도, **Structurizr**는 같은 시스템을 여러 C4 관점에서 보여줄 때 쓴다. |
| 제목의 계층, 공간 스케치 | **markmap**은 제목·목록을 가지로 펼친다. **Excalidraw**는 좌석 배치처럼 직접 정한 위치가 의미를 가질 때 쓴다. |
| 신호와 악보 | **WaveDrom**은 신호가 바뀌는 시점, **abcjs**는 음높이·길이가 주어진 악보에 쓴다. |
| 수치 비교와 통계 | **Vega-Lite**는 표의 열을 축에 연결하는 차트, **Matplotlib**은 세밀하게 조정하는 정적 그림, **seaborn**은 표본의 분포·그룹 비교에 쓴다. 작업 환경이 Python이면 **Altair**로 Vega-Lite를, R이면 **ggplot2**로 그래프를 구성할 수 있다. |
| 웹에서 탐색하는 데이터 | **Chart.js**는 간단한 웹 차트, **Observable Plot**은 표 데이터를 빠르게 비교하는 그래프, **Plotly**는 확대·값 조회, **Apache ECharts**는 연동되는 대시보드에 어울린다. |
| 맞춤 그림·탐색형 연결망·지도 | **D3**는 데이터에 따라 직접 배치할 때, **Cytoscape.js**는 노드와 이웃 관계를 탐색할 때, **Leaflet**은 실제 좌표·경계가 있는 지도를 보여줄 때 쓴다. |

## 독자가 열 곳에 맞춰 전달하기

- **GitHub README**에서는 직접 지원하는 Mermaid를 코드 블록으로 넣을 수 있다. Vega-Lite·Graphviz 등은 그림을 로컬에서 만들어 상대 경로로 삽입한다. 파일·링크가 저장소 안에서 해석되는지 확인한다.
- **Obsidian**에서는 기본 Mermaid와 로컬 첨부 이미지가 우선이다. 전용 플러그인 문법은 대상 볼트에서 사용 가능할 때 선택한다.
- **네이버 블로그·인쇄·오프라인**에서는 생성한 그림을 함께 전달한다. 네이버에는 첨부하기 쉬운 PNG, 일반 마크다운에는 표시 환경에 맞는 SVG 또는 PNG가 유용하다. HTML 복사용 원고가 요청되면 본문과 이미지 파일을 함께 준비한다. 상호작용이 필요한 경우 정적 그림에 더해 요청에 맞는 로컬 HTML이나 이미 공개된 원본 링크를 제공한다.
- **Quarto·Observable Framework·웹앱**에서는 실제 실행 엔진과 지원하는 코드 블록에 맞춰 대화형 차트를 넣을 수 있다. 화면이 초기화돼 실제 데이터가 보이는지 확인한다.
- **대상이 불명확한 일반 마크다운**에는 로컬 정적 그림과 상대 경로를 기본으로 한다. 사내 원문·데이터의 렌더링은 로컬에서 처리한다. 문서에 그림을 넣는 요청 자체로 외부 호스팅·게시를 진행할 권한이 생기지는 않는다.

## 확인

대상 문서와 함께 열어 상대 경로, 출력 파일, 글자·범례, 원문 수치·연결 방향을 확인한다. 게시 환경에서 직접 실행하기 어려우면 로컬에서 SVG·PNG로 렌더링한다. 다른 도구로 대체했다면 실제 출력을 만든 도구로 기록한다.

일반 호출의 결과에는 **사용한 도구 수/25**와 **적용한 Markdown 표현 수/6**, 대표 결과 경로, 남은 항목을 쓰지 않은 이유를 짧게 적는다. 범위를 지정한 호출은 요청 범위를 기준으로 보고한다. 고유 도구와 표현을 각 범위에서 한 번씩 센다. 예를 들어 GitHub의 `geojson` 블록은 지리 지도 표현 1종이고, GitHub 알림을 여러 유형으로 썼어도 표현 1종이다. 실행해 확인한 출력과 이번에 다시 확인한 기존 출력은 구분하며, 단순 의존성·도구 이름·확인하지 않은 뷰어 기본 문법은 실사용 수에서 제외한다.
